# Review, repair and release

Use this reference for an authorized architecture, draft, revision, production package or readiness review. Apply the checks proportionately to the requested scope. Do not turn a narrow wording edit into an unnecessary full production audit.

## Contents

1. Define success
2. Complete the first attempt
3. Assign review roles
4. Score the actual result
5. Verify observable properties
6. Rank, repair and recheck
7. Stop and hand over
8. Cold-start forward testing

## 1. Define success

State the required content, audience, authorized outputs, current guidebook/template, applicable reference lessons and explicit author preferences. Separate mandatory requirements from useful suggestions and optional bonus criteria. Record unresolved material choices without asking for routine ones again.

Define what completion means for this request. A paragraph edit, essay outline, full DOCX/PDF and operational deployment have different completion evidence. A competition-appropriate proposal is not automatically a working, funded or authorized operation.

Do not invent a universal prototype, M2/M3, field-pilot or PoC gate. Apply only the actual rule or evidence needed for the claim. Do not use this principle to excuse an unsupported claim of achieved performance.

## 2. Complete the first attempt

Produce a complete first result before calling the review loop finished. For a production task, that includes the actual audience file and necessary supporting outputs, not just an outline, planned corrections or source code. For an outline task, complete the argument and paragraph architecture without manufacturing an unrequested full submission.

Preserve the artifact snapshot being reviewed: filename/version/hash, exported file identity and what source it came from. A reviewer can critique an earlier candidate while the producer edits, but must not claim clearance of a newer uninspected output.

## 3. Assign review roles

Choose independent roles for distinct consequential questions. Several roles may be combined for a smaller task. Avoid six agents rewriting the same paragraph without a bounded question.

| Role | Core questions | Expected evidence |
|---|---|---|
| Skeptical competition judge | Does the proposal answer the theme/rubric? Is the mechanism distinctive and worth pursuing? Does the core stand alone? | Specific passages, missing bridges, fair comparisons and rubric consequences. |
| Voice/reader editor | Can a new reader picture the system? Do paragraphs develop a connected argument in the author's register? | Actual openings/endings, concept load, jargon and duplication. |
| Evidence reviewer | Do sources support the exact claims with correct scope and status? | Source locators, populations/years, citation-reference consistency and concrete overclaims. |
| Quantitative reviewer | Do models, tables and impact counts reconcile? | Independent reconstruction of decisive arithmetic, units, denominators and scenario boundaries. |
| Operations/domain skeptic | Do participants, authority, resources and failure paths form a credible system? | Concrete contradictions or missing interfaces, not a generic list of validation demands. |
| Design/document reviewer | Is the actual file readable, compliant, compact and navigable? | Rendered page observations, image/table size, link targets and export defects. |

When separate agents are available, give a bounded task and the artifact/reference material they need. Do not call a review independent if the same author performed it. A quantitative model's author can review its audience explanation but is not an independent reproducer of their own calculation.

When separate agents are unavailable, perform distinct documented passes. State that limitation honestly. Do not invent critic exchanges, reader tests or reviewer approval. Reviewer names or role labels do not substitute for actual inspection.

## 4. Score the actual result

Score each applicable dimension from 0–10 with observable strengths and defects:

| Dimension | What it assesses |
|---|---|
| Task fulfillment | The actual request, audience, genre, output scope and explicit constraints. |
| Correctness | Factual support, interpretation, calculation, behavior and formatting where applicable. |
| Completeness | Essential argument and implementation content; requested components and meaningful handover. |
| Clarity and usability | Reader comprehension, cadence, information order and navigation. |
| Presentation/execution | Actual file/layout, visual readability, reproducibility and completed verification. |

Adapt the dimension to the role and mark genuinely inapplicable checks with a reason. Do not use an N/A label to hide missing required work.

Calibration:

- **5:** substantial revision is required.
- **7:** usable, with clear weaknesses.
- **8.5:** strong, with only minor issues that do not leave a critical error or explicit requirement unmet.
- **9:** exceptional supporting evidence is needed for the judgment.
- **10:** reserved for an extraordinary breakthrough; not a routine target or a reward for effort.

Scores are editorial judgments, not probabilities of winning. A polished layout does not offset a wrong calculation. An exact source register does not offset an unexplained mechanism. Do not average away a critical error. Never raise a score merely to pass a threshold or credit a source-only intended fix as an actual repaired artifact.

## 5. Verify observable properties

### Argument and evidence

- Read the continuous core with appendices closed.
- Check the proposal's actors, work, payer/resource model and distinctive mechanism.
- Confirm problem-to-mechanism and mechanism-to-contribution bridges.
- Inspect decisive source claims, scope and citations.
- Separate facts, designs, projections, targets, illustrations and achievements.
- Confirm present participation/funding is not invented from prospective roles.

### Numbers and methods

- Reconstruct decisive arithmetic and unit/denominator conversions.
- Reconcile narrative headlines, table bodies, charts and source calculations.
- Check weight totals, weighted products and scale meanings.
- Check time schedules, cash timing, staff capacity, cost duplication and funding status.
- Preserve equal-workload comparators and separate volume/mass uncertainty.
- Confirm simulation inputs, dependencies, seed/draw order and interpretation.

Do not rerun a previously verified unchanged model merely because a caption moved. Recheck when inputs, formulas, aggregation, display conversions or unresolved numerical concerns change.

### Document and images

- Render through the intended output path and inspect every page.
- Measure counted pages using the actual rule; verify fonts, margins and spacing.
- Check headings/navigation attach to the first substantive exhibit.
- Check all table continuations, repeated headers and note placement.
- Inspect chart labels, units, arrows, legends and physical size.
- Enlarge actual UI detail and preserve faithful source state.
- Decode the embedded QR and compare its intended URL.
- Check actual public access/release scope when it affects the caption.
- Test both link existence and semantic destination in each required format.
- Scan for drafting residue, inherited identities, comments, tracked changes and accidental placeholders.
- Validate DOCX/ZIP integrity and reopen the exact final file.

Automated results support these checks. They do not replace source reading, argument judgment or visual page inspection. A script can pass while a table border export collapses to a page edge; inspect the actual file.

## 6. Rank, repair and recheck

Rank issues by consequence:

1. Critical factual, numerical, scope/authorization or explicit-rule failures.
2. Missing causal/implementation links and misleading interpretation.
3. Reader comprehension, information order and evidence/navigation problems.
4. Layout, density, wording and visual polish.

Record the issue, artifact location, smallest sufficient repair, owner and actual verification needed. Preserve useful content rather than restarting the proposal or design system for a localized defect.

Revise and recheck the affected area plus plausible downstream consequences. A changed paragraph can move a heading or exceed the page limit. A terminology replacement can corrupt a substring in an unrelated word. A new screenshot size can create sparse spill pages. A source-table change can leave a chart stale.

Check the new actual result before closing an issue. “Fixed in the builder” is not “verified in the DOCX.” If an export fails despite valid source formatting, isolate the export process and inspect a fresh result. Preserve the final correct artifact identity.

## 7. Stop and hand over

Use up to **four review-and-revision rounds**. Stop when every applicable dimension reaches at least **8.5**, no known critical error remains and all explicit requirements are met. Do not prolong the loop without a concrete improvement. If the fourth round still has a material unresolved limitation, deliver the strongest defensible bounded result and state that limitation outside the audience file; do not inflate scores or claim unconditional readiness.

Keep scores, critic exchanges, execution logs, tool names and process commentary outside the submission unless the user asks for them. A backstage project record can retain enough factual verification history for continuation without reproducing every debate.

Give a brief handoff containing the requested outputs and any material remaining owner action or verification gap. Do not claim perfection, guaranteed judging outcomes, checks not performed or external submission/publishing that did not occur.

Record the completed version, exact final files, actual count/format/link checks, source/assumption boundaries and current decisions. Archive historical drafts as historical. If final saving changes only metadata, verify the file identity/content relation as appropriate without needlessly repeating the full review.

## 8. Cold-start forward testing

Use this when assessing the reusable kit rather than a single essay. Give a fresh agent the entry instructions and a realistic new request on another topic. Supply only the task-local brief, guidebook and necessary evidence. Do not leak the expected answer, suspected defect or a checklist of fixes that allows the agent to reconstruct success from the evaluator's hints.

Evaluate the actual output against the held-out request and rules. A useful short test can assess whether the agent:

- Selects the correct planning/drafting mode.
- Reads the relevant source material rather than treating a reference as a new fact.
- Develops a visible system with a plausible resource/implementation route.
- Selects only decision-useful frameworks.
- Keeps project-specific case facts out of the new proposal.
- Produces a coherent paragraph architecture and accurate exhibit plan.

For production code, run representative examples: long labels, narrow numeric columns, a multi-page table, a source note near a break, a tall screenshot, a hyperlink target and actual chart data. Judge the real emitted artifacts. Use separate work folders so one test does not accidentally inherit the previous answer.

Record what was tested and its limits. A short cold-start test is evidence of that behavior, not proof that every model, language, document size or rendering environment will work automatically.
