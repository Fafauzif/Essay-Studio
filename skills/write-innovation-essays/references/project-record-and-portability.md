# Project record and portability

Use this reference when starting a project folder, handing work to another assistant, recovering after context loss or packaging a reusable repository.

## Contents

1. Separate reusable method from project facts
2. Project state
3. Source and asset identity

## 1. Separate reusable method from project facts

The reusable workflow carries writing principles, evidence discipline, exhibit patterns, calculation methods and production checks. Each case carries its own idea, guidebook, participants, sources, assumptions, figures and current authorization.

Do not generalize these JejakBalik decisions as universal defaults:

| Case-specific fact/choice | Reusable lesson |
|---|---|
| Five counted main pages. | Verify the actual page rule and budget the main argument accordingly. |
| UI/Depok as the first area. | Explain a complete first operating configuration within the wider route. |
| Institution-funded electronics-return coordination. | Make the payer/resource bargain and operating roles visible. |
| A.1 prototype QR. | Include access evidence where it serves this submission; verify its target and release scope. |
| Approved 10 pt appendix tables. | Check present rules/author permission and actual readability. |
| Reserved cover placeholders. | Respect the current author's cover instruction and identify their completion item. |
| 2027–2036 roadmap. | Match strategic horizon to the proposal and avoid inventing precise far-horizon revenue. |
| Particular financial mix, fees, seed and inputs. | Reuse coherent equations and assumption disclosure, not favorable case numbers. |
| Current local source vs older public demo. | Preserve provenance and do not imply deployment from a local screenshot. |

Preserve settled decisions when continuing a case. Reopen them only when new evidence shows a contradiction, a rule changes or the user requests another direction. Historical drafts and earlier context files are references to lineage, not instructions to roll the project backward.

## 2. Project state

Maintain a compact current state at the top of a detailed handover:

- Current task/mode, authorized outputs and what is complete.
- Audience, language, guidebook/version and applicable rubric.
- Adopted thesis, distinctive mechanism and intended operating picture.
- Settled choices and the reason for consequential ones.
- Exact present evidence/assumption/achievement boundaries.
- Current source files and final artifact identities.
- Known source gaps and any user decision to use available material.
- Open material choices, with dependencies and next safe action.
- Actual checks performed and any unperformed verification.
- External actions not yet authorized or not performed.

A detailed record may include paragraph architecture, complete exhibit data, financial equations, source scopes, comment ledger, asset provenance and a recovery archive. Keep that depth discoverable through headings/indexes. The short entry point should point to it when relevant; do not load a 40,000-word case record for every unrelated essay.

Retain explicit user feedback with selected passage/context and individual IDs. Repeated comments can reinforce a preference; do not silently collapse them into one anonymous instruction. Add actual implementation/verification evidence separately. Do not label a comment “accepted by user” when only an editorial reviewer closed it.

## 3. Source and asset identity

Preserve original files byte-exact where they are part of the private reference archive. Record SHA-256, bytes, meaningful title, original filename, source identity, current role and duplication relation. Keep original ZIPs as well as safe extracted contents. Reject archive paths that escape the destination.

Store derivatives distinctly: OCR text, page thumbnails, crops, render PNGs, chart source and compiled images. A derivative's existence does not prove the original's complete readability. Preserve missing-page and microtext limits in the catalog.

Do not expose internal filenames, persistent IDs, tool references or local paths as audience citations. They are appropriate in a backstage recovery record, where exact retrieval matters. Use meaningful titles and real bibliographic details in the essay.

Record actual screenshot capture source/state, image transformations and commit/release when relevant. Preserve conceptual/observed distinctions. Record a model's input data/version, units, generator/seed/order and output definitions. A future assistant should recover values from source data, not infer them from a screenshot.

## 4. Environment capability

Cloning a repository supplies files and instructions. Producing output also requires the agent's actual environment to provide the necessary capabilities. Check file access, code execution, source retrieval, dependencies, fonts, chart compilation and document/PDF rendering before promising a verified production result.

Use relative project paths and documented inputs. Do not require a previous chat's scratch directory, proprietary tool namespace, private machine path or hard-coded identity. Detect the available tool and route the task accordingly.

| Capability absent | Honest response |
|---|---|
| Repository/file access | Use supplied attachments or ask for the specific material needed. Do not claim a clone/read. |
| Web/source access | Use supplied checked sources within scope and identify any consequential unverified current fact. |
| LaTeX compiler | Preserve source/data and use an authorized accurate alternative if it meets the task; do not claim compiled inspection. |
| DOCX/PDF renderer | Produce what is feasible but identify final pagination/layout checks as unperformed. |
| Required font | Resolve an authorized actual font or state the formatting gap; do not silently substitute and certify compliance. |
| Image generation | Use supplied imagery/exact schematics or deliver an asset brief; do not claim generated assets. |
| Subagents | Use distinct passes and state that independent review did not occur. |

Use only capabilities actually present. A generic skill can state a role and intended tool action without assuming a particular vendor's API name. Do not install, publish, deploy or contact others merely because a project instruction describes those future capabilities.

## 5. Version and review identity

Record what each review inspected: source filename/hash, rendered file/hash, relevant pages and scope. A later source or export may need an affected-area recheck. Do not combine an old good layout screenshot with new unrendered text and call the whole file verified.

Preserve the current canonical model separately from display labels and derived charts. If only wording changes, verify that numeric sequences did not change rather than running unnecessary new experiments. If a formula/input changes, regenerate dependent results and check all affected tables/charts/headlines.

Use atomic writes and file integrity checks where the production tool supports them. Validate the actual completed archive. Do not package transient credentials, local caches, dependencies, reviewer working files or unrelated user files. The private reference archive may intentionally retain original author information; audience templates must not inherit it.

When workspace maintenance removes local files, recover from the durable archive/library/repository where available. Do not infer that the user deleted them. Do not ask the user to recreate a file that can be recovered from its known identity.

## 6. Resume prompt

Adapt this to the actual case:

> Read the current project record, applicable guidebook and current artifact before substantive changes. Read the full V5 manual when applying that workflow; excerpts are not a complete read. Preserve the adopted thesis, operating roles, evidence boundaries and settled choices. Continue only my present request. Use ambitious, natural [Indonesian/English] prose and the approved visual/document preferences. Explain the mechanism and implementation in the core; put inspectable detail in compact navigable appendices. Ask only for a material unresolved choice that the record does not answer. Do not publish, deploy, contact partners or submit without authorization.

The handover preserves context; it does not install permanent memory in another model or guarantee that a future environment has the same tools.
