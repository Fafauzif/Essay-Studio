# Visuals, charts and imagery

Use this reference to choose an exhibit format, adapt a visual reference, prepare accurate chart inputs or commission conceptual imagery.

## 1. Choose the visual's purpose

State what a reader can determine from the visual. Examples: the root causes a design addresses, the sequence of custody decisions, the payer/work relationship, a comparison at equal workload, a time dependency, the cost of growth or the sensitivity of a financial conclusion.

Choose a table for exact mappings/comparisons; a diagram for branching, order or responsibility; a chart for a numerical relationship; a screenshot for actual interface behavior; and a conceptual image for an intended physical/service arrangement. Do not add an image merely to break up text.

Preserve the author's preference for restrained analytical exhibits. These are essay figures, not slides: no slide-name banners, decorative key-takeaway cards, generic self-explanations or invented internal-source citations. Clear labels, a concise caption and an essential source/assumption note should do the work.

## 2. Learn from the supplied references

Use ReFeel and Dua for measured analytical layout, nested market diagrams, careful flow/canvas composition and the combination of exact LaTeX graphics with occasional conceptual imagery. Use ReGenCity for coherent document hierarchy and appendix treatment, subject to the current guidebook. Use actual reference essays to understand how visual evidence sits inside a connected argument.

Inspect the example's content as well as its appearance. A layout reference may contain inconsistent labels, incorrect weights or a weak factual claim. A chart's pleasant palette does not validate its data. Record “what to learn” separately from “what not to copy.”

Use the visual catalog to choose relevant examples. Read the selected essay/plan fully when drawing writing or operating lessons from it, and inspect the selected visual at readable size. Do not claim a new complete reading of the whole reference archive on every run.

## 3. Native tables, TikZ and numerical plots

Use native Word tables first for editable financial rows, weighted matrices, RACI, SMART definitions, risks, stakeholder roles and source mappings. If a table fits naturally, do not rasterize it merely to avoid table layout.

Use LaTeX/TikZ for precise diagrams and PGFPlots for appropriate data-based charts. Keep chart data in an auditable JSON/CSV or source table; generate labels and values from that data where possible. Use calculation tools for computation and the rendering tools for presentation. Avoid hand-retyping numerical results into several independent chart sources.

| Family | Required input discipline | Design/interpretation check |
|---|---|---|
| Horizontal issue tree | Explicit parent-child hierarchy; leaf evidence and response mapping. | Branches do not cross or imply an unsupported hierarchy; source scopes remain clear. |
| Service flow/swimlane | Stages, responsible actors, decisions and exception/return paths. | A yes/no branch has meaningful destinations and no stranded case. |
| System overview | Intended roles and flows or faithful source scenes. | Distinguish service design from implemented/operating proof. |
| TAM/SAM/SOM | Population/eligibility, reach, time, price and usage assumptions. | Boundaries are defined; schematic circles do not imply measured area shares. |
| Gantt | Tasks, dates, durations, dependencies and milestone outputs. | Service/revenue does not begin before required readiness. |
| Risk heatmap | Defined likelihood/severity scales and IDs matching the register. | Caption identifies initial/residual positions correctly. |
| Financial bars/lines | Currency/year, revenue/cost/cash definitions, horizon and scenario. | Axes/series agree with tables; funding is not mistaken for revenue. |
| Sensitivity/tornado | Base case, one-variable changes and common method. | Direction/units clear; nonlinear staffing thresholds are retained. |
| Monte Carlo distributions | Sample count, seed, distributions, dependencies and output definition. | Quantiles/frequencies are conditional on assumptions, not measured market probabilities. |
| Driver chart | Exact association/sensitivity method. | Rank association is not labelled as a causal effect. |
| Competitor map | Evidence for criteria/placement and comparable scope. | No arbitrary self-favoring positioning disguised as measurement. |

The same reference can support several formats. A four-column problem mapping may work as a native table for one project and a TikZ tree for another. Choose the format with the clearest reading relationship at the available physical size.

## 4. Physical-size design

Set the placed width in centimeters before judging label size. A high-resolution PNG can still contain unreadable 5 pt labels when reduced. Inspect the exported document at the actual size, not only a large source preview.

Use consistent typography and a limited project-appropriate palette. The author's preferred reference palette is black text, forest green, pale sage and white with light neutral rules. This is a reusable taste option; the guidebook's mandatory monochrome or brand treatment takes precedence. Do not force a project's app font into a Times New Roman essay.

Check:

- Actual font availability and embedding/resolution in the final export.
- Long Indonesian labels, currency strings, decimal separators and units.
- Deliberate line breaks at words, not inside “Institusi” or another ordinary label.
- Adequate margins/padding and aligned label blocks.
- Arrows that terminate visibly and do not pass through unrelated nodes.
- Consistent numeric rounding between charts and tables.
- Legends and captions that describe exactly what is shown.
- Aspect ratio, readable axis ticks and contrast without heavy decoration.

For a dense exhibit, simplify hierarchy, divide a true subproblem, use a companion data table or enlarge the figure. Do not compensate with tiny fonts or remove a decisive source boundary. A table title may be shortened from a long category name to an accurate “Kode” when its function is simply a code column.

Use native editable equations when a document equation is required. Do not leave literal caret syntax in prose as a substitute for finished mathematical presentation. A plain-language equivalent is acceptable when it communicates the intended calculation more naturally.

## 5. Screenshots and conceptual images

Use actual screenshots when documenting an existing prototype or website. Retain the capture date, source release/commit or observed page, state and crop. A crop can focus attention; it must not change a price, status, disabled control or relevant limitation. Keep enough context for the caption to be truthful.

Inspect both public and locally run versions when the distinction affects the access claim. A public URL may serve an older interface. A source-code link and a local screenshot do not establish that the current source is deployed. Do not update a deployment without authorization merely to make a figure/access claim convenient.

Group captures by decision. A full network overview can accompany concise custody/data-hold states. A tall options panel can sit beside an approval view in a native table. Use a faithful form crop rather than a tiny form inside a large darkened full-screen capture. Recheck the whole page after changing sizes: enlarging one panel can create several half-empty spill pages.

Use GPT Image or another available image-generation capability for conceptual mockups, physical service scenes or explanatory illustrations when they add meaning. Label them as concepts where a reader might otherwise infer an actual operating site or measured outcome. Never use generative output to recreate proof screenshots or render exact numerical charts.

If image generation is unavailable, use supplied assets, an exact schematic or an asset brief. Do not claim that a generated file or tool call exists. The portable workflow must not depend on a particular proprietary tool name being present.

## 6. Image-generation briefs

Adapt these briefs to the present project. They are templates, not instructions to generate an image in every essay. Keep tool/process commentary out of the image and final audience file.

### Conceptual service or physical arrangement

> Create a finished conceptual illustration for an innovation essay about [defined service]. Show [specific actors/objects] performing [specific action] in [setting]. Make the spatial relationship between [stage A] and [stage B] understandable. Use [chosen visual style/palette], restrained composition and realistic physical proportions appropriate to the concept. Preserve supplied reference identities and object details. Include no invented partner logos, approvals, numerical performance claims, fake interface data or decorative explanatory paragraphs. Leave labels/citations to the document layout. Output [aspect ratio/resolution]; [transparent background only if required].

### Proposed interface mockup

> Create a conceptual interface mockup for [user] completing [one task]. Show the decision-relevant state, the inputs needed, the main action and the consequence of that action. Use the supplied language, terminology and design reference. Keep typography legible and layout restrained. Do not invent measured performance, testimonials, partnerships or a working connection to an external system. Mark this as a concept in the surrounding document. If an actual interface capture exists, use that capture for evidence instead of a recreated mockup.

### Consistent conceptual scene series

> Produce [number] coordinated concept scenes showing [stages]. Keep camera angle, scale, palette, lighting and recurring object identity consistent. Each scene should depict one meaningful stage with sufficient context to connect it to the next. Do not change the object's condition to imply an achieved repair/recovery unless that stage is explicitly a proposed illustration. No slide titles, decorative callouts, invented text or numerical labels. The document will supply concise stage labels and source/status captions.

When editing supplied images, inspect them first and use tools permitted by the current environment. Preserve transparency when relevant and retain exact source material for evidence. A faithful crop and a generative alteration are different operations; do not describe one as the other.

## 7. Provenance and verification

Keep a figure register: ID, role, source paths, original bytes/hash, crop/transform, data/version, renderer/source, physical size, output files and verification status. Audience captions use meaningful provenance; the register can retain technical details internally.

Render a source and inspect it. Embed the actual verified image and compare its bytes or hash when necessary. Render the final DOCX/PDF and inspect every page. A correct `.tex` file does not prove the document contains its latest output.

Repair clipping, source-note-only continuations, tiny screenshots, malformed labels, inconsistent IDs and stray export lines. If an export failure appears despite valid source formatting, make a fresh isolated export and inspect the result. Do not silently accept the broken output because the source code looks right.
