# Essay workflow

Use this reference for a new innovation-competition project or a substantive restart after new rules, evidence or author decisions. Use only the relevant stages for a bounded edit. The full supplied Innovation Essay Hub V5 remains the normative writing manual; this file makes the production sequence repeatable.

## 1. Authority and mode

Resolve conflicts instead of stacking incompatible instructions. Respect governing platform requirements, truthful evidence use, actual competition rules and the user's current authorized scope. The guidebook governs eligibility, permitted assistance, formatting, page limits and submission. The author's current decisions govern the proposal. V5 governs persuasive development and evidence-proportionate confidence. Reference essays supply observed writing/design lessons, not new competition rules or facts about the present project.

Identify the requested mode before acting:

| Mode | Appropriate work | Do not infer |
|---|---|---|
| Discuss | Explain alternatives, develop mechanisms, recommend a direction, ask consequential questions. | Authorization to produce a full package or install tools. |
| Outline | Recommend a thesis, paragraph sequence, page budget and exhibit plan. | Authorization to write the complete submission. |
| Draft | Write the requested text or complete authorized draft. | Permission to fabricate missing empirical support. |
| Produce | Build the authorized files, calculations, figures, links and render checks. | Permission to publish, deploy, contact partners or submit. |
| Revise | Inspect the current source, comments and selected scope; make and verify changes. | Permission to change settled product decisions without a concrete contradiction. |
| Review | Evaluate the actual supplied artifact and repair if authorized. | Permission to describe an unrendered intention as a verified final file. |

When the user explicitly requests end-to-end production, continue through a reviewable result. Do not stop at a plan or ask again for routine formatting choices already authorized. When the user says to plan before creating a ZIP or document, remain in planning mode until production is requested.

Ask before a material assumption changes the proposal's scope, conclusions, financial interpretation, outcome meaning or participant commitments. Resolve routine wording, table widths, file organization and approved design preferences independently. Ask a small number of high-leverage questions rather than a questionnaire covering information already present in the files.

## 2. Intake and complete reading

Read all newly supplied project documents completely before substantive work. Preserve the actual current versions. An old summary does not override a later edited file. For a library of prior examples, use the catalog to select relevant items, then read the selected examples completely before claiming their lessons. Do not assert that an unselected archive was newly read.

Create a compact intake record containing:

- Current request, audience, language, authorized outputs and current mode.
- Guidebook title/version and any organizer clarification.
- Required structure, rubric, eligibility, AI policy and administrative steps.
- Page/word limits and exactly what is included or exempted.
- Typography, margins, spacing, cover, header/footer, logos, file type and naming.
- Current author decisions and explicit dislikes/preferences.
- Source inventory, page counts, extraction method and precise access gaps.
- Reference examples selected and what each is being used to learn.

Extract text and inspect substantive visuals. A successful text extraction does not establish that scanned pages, equations, diagrams or comments were read. For DOCX feedback, extract comment IDs, full comment text and its selected passage; retain duplicates separately. For archives, enumerate members, identify duplicates by content hash and preserve the original archive. Use OCR for scans while retaining visual inspection of meaningful pages. Report exact missing pages, cut-off text or illegible labels; do not infer the rest from a heading.

If the author has already authorized use of available information and cannot supply the missing original, record the specific limit and proceed within it. Do not repeatedly ask for the same unavailable pages. Distinguish a gap in an inspiration essay from missing evidence needed for the present proposal: they have different consequences.

Read V5 completely through its end marker before applying it in a new context. Give the brief V5 receipt when appropriate: developed-system advocacy, evidence-proportionate confidence, validation as a targeted implementation tool and deliberate reading cadence. A receipt is an acknowledgement, not a substitute for checking the output.

## 3. Define the argument

Write a short working proposition before selecting frameworks:

1. **Problem:** identify the affected group, consequential condition and binding barrier.
2. **System:** specify the intended operating arrangement, actors, decisions and flows.
3. **Warrant:** explain how the mechanism changes that barrier and what supports the explanation.
4. **Choice:** compare a credible existing response under relevant criteria.
5. **Realization:** connect the present position to funded, staffed, governed and sustained operation.

Follow one representative participant, transaction, object or institutional decision through the proposed arrangement. Identify the payer or resource owner, the work purchased or supported, the operator, the beneficiary and the reason each participates. A feature list cannot replace this operating picture.

Classify every consequential claim: checked fact, proposed design, causal explanation, conditional projection, comparative recommendation, target or observed achievement. Match support to that claim. A clearly specified design does not require proof of achieved impact. A claim of measured performance does. Do not invent a universal prototype, PoC, field-pilot or maturity requirement when the competition does not impose one.

Develop the adopted idea confidently. Challenge a real contradiction with a concrete explanation. Do not restart product discovery because a new assistant receives the project or because a component is proposed rather than already operating.

## 4. Plan the body and exhibits

Build a paragraph-level outline. Give every paragraph one main job and a transition to the next necessary question. Typical jobs are context, diagnosis, mechanism, comparison, financial interpretation, implementation or contribution. Vary paragraph weight where the explanation requires it; do not enforce a fixed sentence count.

For a proposal with an evidence-led opening, the sequence often runs:

1. Significant condition and selective context.
2. Specific unresolved barrier and current responses.
3. Clear definition of the intended system at the agreed introduction point.
4. Distinctive mechanism and representative operation.
5. Participation, resources and implementation logic.
6. Quantified or otherwise observable intended contribution.
7. A synthesis of the recommendation established by the essay.

This is a reasoning sequence, not a compulsory set of headings. An author may expressly reserve all solution exposition for Gagasan; honor that. A different guidebook may require another architecture. Citation counts, section names, page counts and intro placement are project settings.

Budget pages using the actual rules. Reserve cover/reference pages only when they count. Allocate most explanatory space to the proposal and its implementation when that is where the rubric's feasibility/innovation judgments occur. Retain the central mechanism, fair comparison and headline result in the body. Move derivations, full mappings and evidence inspection to appendices only if the core argument survives with appendices closed.

For every candidate exhibit, specify a job: the reader's question, supported body claim, input source/assumptions, suitable format, calculation or classification, physical size and intended decision. Reject an exhibit that repeats another without a distinct use. See [appendices-and-navigation.md](appendices-and-navigation.md) and [frameworks-and-implementation.md](frameworks-and-implementation.md).

## 5. Draft the complete first attempt

Draft a complete argument before treating it as a finished document. Explain ordinary functions before branded labels or acronyms. Place interpretation beside demanding evidence. Explain why a proposed configuration is useful rather than repeatedly calling it innovative.

Use external sources for external facts, transparent assumptions for projections and real observations for achievements. A planning assumption should be identified once at its consequential scope, with a sensitivity or implementation response where useful. Do not finish every paragraph with a generic validation warning. Do not omit a decisive uncertainty merely to sound confident.

Introduce the institutional or business purchase in operational terms: what changes for the buyer, which work is performed, what is paid for, how the service is reconciled and why it is worth renewing. Avoid reducing feasibility to a tariff and an NPV figure. A service may be funded through a public, community or institutional arrangement rather than a commercial sale; explain that arrangement honestly.

For the conclusion, synthesize the diagnosed barrier, developed mechanism, supporting rationale, intended contribution and implementation direction already established. Do not add a new operating checklist, unsupported national impact, unrelated source or automatic “more research is needed” ending.

Read the continuous prose. Use [writing-and-voice.md](writing-and-voice.md) for a factual and cadence pass before locking text for layout.

## 6. Produce the document

Start from an authorized clean template or neutral house style. Remove inherited author identities, old cover text, unused comments, tracked changes and irrelevant template decoration. Supply required logos and cover fields from the current competition; do not borrow them from a previous project.

Keep content, evidence and style settings separate. Build editable native paragraphs and tables. Insert exact diagrams/charts from tested source files. Use actual captures for prototype evidence and generated conceptual imagery only for its stated conceptual role. Supply meaningful captions and units; keep process chatter out of the audience file.

Create real internal links at the supported claim, a specific appendix index and visible returns. Keep headings/navigation attached to the first substantive exhibit, figures attached to captions and source notes attached to meaningful data. Let appendices flow continuously. Add a page break when the structure genuinely needs it, not automatically at every appendix.

Render the actual file, count the actual pages and inspect every page. Check the real font, image size and all table continuations. Inspect exported links and a QR's encoded target; a QR label is not proof that its site currently shows the same software release.

Use the current scripts' documented interfaces. Never hard-code a prior chat's scratch path, proprietary tool identifier or environment variable into the portable workflow. Detect available renderers/dependencies and report an exact unperformed check if a required capability is absent.

## 7. Review, repair and release

Run the bounded review loop in [review-and-release.md](review-and-release.md). Review the complete first attempt against the actual request and references. Use independent agents when available and appropriate; otherwise perform distinct passes without claiming independence. Fix critical errors first, then argument/reader weaknesses, then polish. Recheck affected areas for regressions.

Stop when all applicable dimensions meet the honest 8.5 threshold and no known critical error or unmet explicit requirement remains, or after the fourth review-and-revision round with a clear, concise statement of material unresolved limits. A score is an editorial assessment, not a forecast of competition results. Never increase a score solely to pass.

Reopen the exact delivery file, verify ZIP integrity for DOCX/ZIP, confirm hashes and save the requested deliverables. Keep ratings, critic exchanges, tool logs and production commentary outside the submission. A reserved cover placeholder requested by the author is an explicit completion item; do not imply a fully submitted package when that remains or when organizer submission has not occurred.

## 8. Resume an existing project

Read the current project handover and actual current artifact. Recover the latest guidebook and evidence only where needed. Preserve settled decisions and distinguish current state from historical examples. A previous review clears its inspected snapshot, not future edits or a different export.

For a narrow revision, extract the affected requirement, edit the authorized scope, inspect the changed artifact and relevant downstream effects. Do not rerun every model or create a new framework dossier for a reversible wording change. Use the source archive to recover lost production files; do not infer missing equations from a screenshot when reproducible inputs exist.

Record the new version, what changed, which checks were actually performed and what remains. A later assistant should be able to continue without being told the entire conversation again.
