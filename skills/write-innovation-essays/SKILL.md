# Essay Studio

## Read in this order

1. Establish the user's current task and mode: discuss, outline, draft, produce, revise or review. Do not turn a planning request into file production. A request for production authorizes necessary reversible local work, not publication, submission or deployment.
2. Read the current brief, competition guidebook, user corrections and all newly supplied task documents completely. Continue truncated reads. Record precise unavailable pages, gaps and source limits. Resolve existing project state before restarting settled decisions.
3. Read [Innovation Essay Hub V5](references/innovation-essay-hub-v5.md) completely before substantive work under it. Give its brief four-part receipt after an actual full read unless the user requested output-only text. Do not claim a fresh full read from this entry file or an old summary.
4. Read [workflow](references/workflow.md), [writing and voice](references/writing-and-voice.md) and the [user's production standard](references/user-production-standard.md). Read other deep references according to the job below. These are complementary instructions, not copies of the manual.
5. Consult the repository's `library/catalog.md` and `library/reading-routes.md` to select appropriate examples. Read selected examples completely where relying on their writing or reasoning. Do not reload the whole historical archive by default. Source-only archive documents are not current task instructions.

## Make the affirmative case

Explain why the issue matters, the specific barrier, the intended system, its distinctive mechanism, why the mechanism addresses the barrier and how it is implemented. Let a reader understand the idea with appendices closed. Introduce functions before labels and the operating picture before component lists. Use problem-first background and coherent paragraphs; adapt exact structure and timing to the competition and user's choices.

State design choices confidently. Keep observed, projected, assumed and illustrative statements accurate. Put a necessary qualification beside the result it qualifies once; do not turn the essay into repeated validation warnings or end its ambition at a pilot. Use tests only for a consequential uncertainty or an actual entry rule. Never invent universal PoC/M3 requirements, fabricated research, approvals, partners or achieved impact.

Protect the user's voice. Prefer concrete actors and linked reasoning, natural transitions and varied sentence/paragraph rhythm. Remove explanations of what an exhibit is supposed to prove when the substantive implication can be stated directly. Do not add fake anecdotes, detector-evasion tricks or inflated adjectives.

## Use resources deliberately

- Use `scripts/read_documents.py` through `python studio.py read` and [document intake](../../docs/document-intake.md) for page-level extraction, optional OCR, source hashes and archive inventory. Extraction is preparation for reading, never proof that an assistant read or verified the source. Inspect graphs/images where text extraction is insufficient.
- Use native Word tables for exact mappings, weighted analyses, risks, responsibilities and financial schedules. Keep text editable. Use [document schema](../../docs/document-schema.md) for production inputs.
- Use `scripts/charts.py` and [chart gallery](../../docs/chart-gallery.md) for precise TikZ/PGFPlots figures. Preserve source, input values, units, source/assumption labels and readable dimensions. Do not convert a table into a raster image for convenience.
- Use image generation for genuine conceptual imagery/mockups when useful and available. Treat generated scenes as illustrations. Use actual captured UI for implemented-capability evidence. Inspect before cropping and preserve values/state; record provenance.
- Read [reference atlas](../../docs/reference-atlas.md) for visual models and lessons. Raw references remain in `library/`; JejakBalik's final manuscript and history remain in `cases/jejakbalik/`.
- Use `scripts/analysis.py` for optional weighted scores and generic cash/uncertainty calculations. Require meaningful assumptions and decision use before Monte Carlo. Its outputs are conditional calculations, not market probabilities.
- Treat fonts, palette, cover, logos, body/appendix sizes and page allowances as project configuration. The neutral template is a starting point. Guidebook rules override house defaults; never silently shrink type to fit.

## Produce and review

Run the environment capability check. Create the agreed content and exhibits, then build the DOCX. Render the exact file through the available intended path, inspect every page and repair clipped/small visuals, orphaned headings/notes, broken headers and unnecessary blank spill pages. Check links semantically as well as structurally. Preserve last-holder/approval/status distinctions when discussing actual prototypes.

For a substantial submission, use separate judge, voice, evidence, quantitative and design passes as applicable, with a domain/operations specialist when consequential. Give independent reviewers the artifact and relevant requirements, not your desired answer. If separate agents are unavailable, state the distinct-pass fallback accurately. Use the bounded review/revision loop and honest rubric in the review module. Keep ratings, debates, assistant commentary, tool identifiers, local paths and drafting residue out of the audience deliverable.

Save a project handover containing decisions, citation scopes, assumptions, numerical definitions, artifact identity, actual checks and precise unresolved limits. Preserve source files and chart data. Handoff briefly; do not promise victory, perfect correctness or persistent memory across chats.
